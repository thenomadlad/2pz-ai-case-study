# Bedashing V1 — the perturbation loop

Date: 2026-10-01. Status: implemented (see `docs/designs/v1-plan.md` for the task
breakdown that was executed).

## Design philosophy

A retail portfolio analyst carries a mental model of how branches map to
demand: which assumptions hold, which signals matter, and how they combine
into a recommendation. This software's job is to encode that model, not
replace it. The model consumes a fixed set of sourced signals and a fixed
set of assumptions, and produces a report — a data artifact an analyst can
act on — visualized so the report's shape is legible at a glance.

The model stays useful only if the analyst can argue with it. So the core
interaction isn't "view the report," it's perturb, re-run, compare: change
an assumption, override a signal that seems wrong, re-run the same model
against the changed input, and see exactly what moved — which branches
flipped, by how much, and why. The report isn't a one-shot output; it's
the left half of a diff whose right half the analyst controls.

## Scope

**In scope:**

- A baseline declared explicitly as an assumptions file + the sourced data
  we already have (v0's seed CSVs) — "reality," computed once.
- Scenarios declared the same way: an assumptions/overrides file, hand-
  edited, that perturbs branch/community signals (including relocating a
  branch) and the two assumptions that still matter once acquire isn't
  re-run (see below).
- Running a scenario and diffing it against baseline, at both the branch
  and community level.
- A diff rendered on the existing map.

**Explicitly out of scope** (see "Next steps" at the end — these are
noted, not silently dropped):

- Capacity or any other not-yet-computed feature.
- Re-running `acquire` per scenario (so acquire-stage-only assumptions
  aren't perturbable yet).
- Overriding computed/processed fields directly (vs. overriding the raw
  inputs that produce them).
- A "promote scenario to baseline" step — baseline never changes except
  by deliberately re-running the real pipeline against new source data.
- Any UI for authoring overrides — scenarios are hand-edited YAML for
  this version, matching v0's "the model is prescribed in code" spirit.
- The model/decisioning logic itself and the report shape
  (`BranchFeatures`/`Decision`) — completely untouched by this design.
  v0's "What's stubbed vs. real" story, zero-API-key fallback, caching,
  etc. all carry over unmodified.

The entire point of this version: don't touch `acquire`/`features`/`model`
as modules. Everything new is orchestration *around* them.

## Architecture

### Baseline — reality, computed once

`data/scenarios/baseline.yaml` formalizes what's currently scattered
across `Settings` defaults into one explicit, versioned, diffable file:

```yaml
assumptions:
  contest_ratio: 1.25
  global_female_share: 0.49
  fallback_price_aed: 99.0
  model_backend: llm
```

(The committed `data/scenarios/baseline.yaml` keeps `model_backend: llm` -- v0's
documented default, with automatic fallback to `rubric` when no API key is set. The
"use `rubric`" recommendation below is specifically for scenario runs, not baseline.)

`just all` reads this file, runs `acquire` → `data/raw/*.json`, then
`features` + `model` → `data/processed/baseline/`. This is the one true
raw dataset and the one true baseline report. Nothing a scenario does ever
writes here. If reality changes — new seed data, a genuinely revised
assumption — you edit `baseline.yaml` and/or the seed CSVs and re-run
`just all` yourself. That's a deliberate act, never an implicit side
effect of running a scenario. There is no "promote" step; baseline doesn't
get overwritten by something you were just trying out.

### Scenarios — hypotheticals, computed fresh each time

`data/scenarios/<name>.yaml`, one file per hypothetical, pydantic-
validated at load time. Two blocks:

```yaml
name: bigger-palm-jumeirah
assumptions:
  contest_ratio: 1.1
overrides:
  branches:
    palm-jumeirah:
      rating: 4.9
    hypothetical-dubai-marina:    # id not in baseline -> new branch
      name: "Hypothetical Dubai Marina"
      lat: 25.0805
      lng: 55.1403
      area: "Dubai Marina"
  communities:
    al-sufouh-second:
      population_female: 9000     # directly supplying a different estimate
```

Running a scenario:

1. Load `data/raw/*.json` (the fixed baseline truth) into memory — never
   read from or written to on disk.
2. Apply `overrides.branches` / `overrides.communities` in memory. An id
   that matches an existing baseline entity is a **patch** (only the
   given fields change); an id that doesn't match is a **new entity**,
   which must supply enough fields to construct a complete
   `Branch`/`Community` (so a typo'd id on an intended patch fails loudly
   at validation — a sparse patch can't accidentally pass as a valid new
   entity, since new entities need the required fields a patch usually
   won't be supplying).
3. Run `features` + `model` against the patched in-memory data, with the
   scenario's `assumptions` overrides applied.
4. Write the result to `data/processed/current/` — fully overwritten by
   whatever scenario runs next.
5. Diff `current/` against `baseline/`, write
   `data/processed/current/diff.json`.

### Why `acquire` isn't re-run per scenario

`global_female_share` and `fallback_price_aed` only affect acquire-stage
imputation (population estimation, price backfill) — they're baked into
`data/raw/*.json` once, at baseline time. Since scenarios never re-run
acquire, a scenario overriding either of those two would silently do
nothing — so the scenario `assumptions` block doesn't expose them at all.
Only `contest_ratio` (features stage) and `model_backend` (model stage)
are perturbable assumptions in V1.

If what you actually want to explore is "what if our female-share
estimate were different," the V1 mechanism for that is overriding the
resulting `population_female` value directly on the communities you care
about — supplying the number yourself — not re-deriving it from a
different global share. Re-running acquire per scenario is a real next
step, not implemented here.

### Diff

Two parts, both needed — a structural perturbation like relocating a
branch can leave that branch's own numbers looking unremarkable while
completely changing which communities feed it:

- **Branch diff**: per branch, which `BranchFeatures`/`Decision` fields
  changed (old → new), and whether `action` flipped.
- **Community diff**: per community, whether `nearest_branch_id` changed.

Frontend: the existing map gains a diff mode. Branches whose `action`
flipped get a highlight ring; communities that got reassigned get
highlighted; the side panel shows old → new per field for a selected
branch.

### Validation

Scenario files are pydantic models, same convention as every other stage
boundary in this codebase. Load-time failures (unknown field, malformed
override, an ambiguous patch/new-entity id as described above) are loud
errors, never silent no-ops.

### Backend recommendation

Use `model_backend: rubric` for perturbation runs by default — free,
instant, deterministic. `model_backend: llm` works, but every scenario
changes the feature vector by definition, so the disk cache never helps
across scenarios (only across repeated runs of the *same* scenario) —
each scenario costs real API calls if you opt into it.

## Next steps (explicitly deferred, not forgotten)

1. **Capacity** (and any other future computed feature) — once it exists
   as a `BranchFeatures` field, it should be overridable the same way
   branch/community signals are now.
2. **Re-running `acquire` per scenario**, so acquire-stage assumptions
   (`global_female_share`, `fallback_price_aed`) become genuinely
   perturbable instead of requiring you to override the resulting raw
   signal by hand.
3. **Overriding processed/computed fields directly** (e.g. a future
   `capacity` field) rather than only the raw inputs that produce them —
   a second `processed_overrides` block, applied after `features` runs.
   Precedence rule for when this lands: a processed-level override for a
   field wins over whatever a raw-level override plus recomputation would
   have produced for that same field.
4. **An interactive UI for authoring overrides.** Roughly 20-30% more
   work than this version, almost entirely in the frontend (a form for
   assumptions is cheap; making side-panel fields stageable/editable is
   the real cost) — the backend orchestrator built here doesn't care
   whether the overrides JSON came from a hand-edited YAML file or a
   POSTed form, so this is additive on top of everything above, not a
   redesign.
