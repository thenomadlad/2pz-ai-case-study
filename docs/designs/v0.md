# Bedashing V0 — scrappy branch right-sizing prototype

Date: 2026-09-24 (design) · 2026-09-30 (last updated)

Status: **built and working end-to-end.** All 16 planned tasks implemented
via subagent-driven development, each reviewed individually; a final
whole-branch review found and fixed 1 Critical + 9 Important issues across
two fix waves. 58 tests passing. Zero-API-key path verified in a real
browser. This is the single design/status doc for the project — it folds
together what was originally two separate docs (a design brief and an
implementation plan) plus a status checkpoint, since the project is done
and that split no longer earns its keep.

## What this is, and what it is not

A deliberately crude, end-to-end prototype for exploring retail branch
decisions for Bedashing Beauty Lounge (a real multi-branch salon chain in
the UAE). The point is a working toy you can poke at within a day — not a
defensible model. It is known to be wrong in the ways listed under
"Known limitations" below. That's not a disclaimer, it's the experiment
log — the value is having something concrete to argue with.

One-sentence behaviour: given branch locations, Dubai community population
(female), and prices, assign each community to its nearest branch, roll
that up into per-branch features, ask an LLM (or a deterministic rubric)
to label each branch PROTECT / HOLD / SHRINK with reasons, and render it
all on a Leaflet map.

Non-goals: isochrones, competitors, Huff/gravity models, authentication, a
database, tests beyond what's needed to trust the pipeline, deployment,
mobile layout, Abu Dhabi/Sharjah (Dubai only).

## Principles

1. File-based pipeline. Each stage reads files and writes files to
   `data/`. No database, no in-memory coupling. Every intermediate
   artifact is human-readable JSON/CSV so it can be opened and argued
   with.
2. Each stage is independently re-runnable and idempotent.
3. Runs with zero network access and zero API keys. Committed seed data in
   `data/seed/` is the primary path; scrapers/APIs are optional
   enrichment that always falls back to seed. A first-time user runs
   `just all` and gets a working map.
4. The decision model sits behind one interface with two implementations
   (LLM and a deterministic rubric) so they can be compared — that
   comparison is the actual experiment.
5. Scrappy means small, not sloppy: type hints, pydantic models at every
   stage boundary, no frameworks beyond what's listed below.

## Stack

- Python 3.11+, `uv` (dependency/venv/lockfile management)
- `httpx`, `pydantic` v2 + `pydantic-settings`, `python-dotenv`
- `fastapi` + `uvicorn` for serving
- Frontend: plain HTML + vanilla JS + Leaflet from CDN. No React, no
  bundler, no build step.
- LLM: Anthropic API via the `anthropic` SDK, structured tool-use output.
- `pytest`, `ruff`
- Task runner: `justfile` (originally a `Makefile`, swapped mid-build —
  functionally identical)

Deliberately avoided: geopandas/shapely (haversine on centroids is
enough), any map tile provider requiring a token (Leaflet + OSM tiles
need none).

## Architecture

Four independently re-runnable, file-based stages, wired together by the
`justfile`. No database — every stage boundary is a JSON file:

```
data/seed/*.csv -> acquire -> data/raw/*.json -> features -> data/processed/*.json -> model -> decisions.json
                                                                                            |
                                                                                            v
                                                                                  serve (FastAPI + Leaflet)
```

```
2pz-ai-case-study/
  justfile
  pyproject.toml / uv.lock
  .env.example
  README.md
  data/
    seed/            # committed — the guaranteed, zero-network path
      branches.csv
      communities.csv
    raw/              # gitignored, written by acquire
    processed/        # gitignored, written by features/model
  src/
    config.py          # pydantic-settings Settings, injectable everywhere
    models.py           # pydantic models for every stage boundary
    acquire/
      branches.py, population.py, prices.py, run.py
    features/
      assign.py          # haversine + nearest-branch assignment
      build.py            # per-branch features + network stats
    model/
      base.py             # DecisionModel protocol
      rubric.py            # deterministic implementation
      llm.py               # LLM implementation
      run.py               # backend selection + entrypoint
    serve/
      app.py              # FastAPI
      static/              # index.html, app.js, style.css
  tests/              # mirrors src/, one test dir per stage
  docs/designs/v0.md  # this file
```

### Stage 1 — acquisition (`src/acquire/`)

Writes to `data/raw/`. Every module exposes `load()` which tries a live
source (if enabled), falls back to seed, and logs loudly which one it
used — live enrichment (`ENABLE_SCRAPE`, `DUBAI_PULSE_ENABLED`) is
intentionally stubbed, see "What's stubbed vs. real" below.

- **`branches.py`** → `Branch{id, name, lat, lng, area, rating,
  review_count, avg_price_aed, source}`, from `data/seed/branches.csv`.
- **`population.py`** → `Community{id, name_en, lat, lng,
  population_total, population_female, is_estimated}`. If a community has
  no reported gender split, estimate it via a global female share and set
  `is_estimated=True` — do not silently impute.
- **`prices.py`** → `backfill_missing_prices()`: fills missing prices with
  the network median, or a documented fallback constant when *no* branch
  has a real price (see "Scope decisions" below — this is the actual case
  for all 9 real branches).
- **`run.py`** orchestrates all three, writes `data/raw/*.json` +
  `price_flags.json`, prints a summary (source per dataset, record
  counts, estimated-field counts).

### Stage 2 — features (`src/features/`)

Pure computation, no I/O. Reads `data/raw/`, writes
`data/processed/branch_features.json` + `community_assignment.json`.

- **`assign.py`**: haversine distance from every community centroid to
  every branch; assigns the community's full female population to the
  nearest one. Also records the second-nearest branch and whether the
  community is "contested" (`second_km / nearest_km < CONTEST_RATIO`,
  default `1.25`) — this is what makes catchment overlap visible without
  any real geometry.
- **`build.py`**: rolls assignments up into `BranchFeatures` (population
  served, pop-weighted mean distance, contested share, sibling
  proximity, price index, `estimated_fields`) plus a `NetworkStats`
  object (median/p25/p75 per feature) so a single branch's numbers have
  something to be compared against.

### Stage 3 — decision model (`src/model/`)

- **`base.py`**: one `DecisionModel` Protocol —
  `decide(branches: list[BranchFeatures], network: NetworkStats) ->
  list[Decision]` (batched, not per-branch — see "Scope decisions").
- **`rubric.py`**: deterministic ~30-line baseline. Normalizes
  `female_pop_served` / `contested_share` / `rating`, sums with equal
  weights, top third PROTECT / bottom third SHRINK / rest HOLD.
  `key_drivers` = the features furthest from the network median,
  normalized by each feature's IQR so population doesn't always win on
  raw scale alone. This is the zero-API-key guaranteed path.
- **`llm.py`**: one Anthropic tool-use call per branch, temperature 0,
  structured `Decision` output. Disk-cached by a hash of (prompt version,
  feature vector, model name) — re-running with unchanged inputs makes
  zero API calls. If the API call fails, falls back to a rubric decision
  computed against the *full batch* (not a lone branch, which would
  always land on PROTECT), marked `confidence="low"` with a caveat
  explaining the fallback, and never cached — a transient failure doesn't
  permanently poison that branch's decision.
- **`run.py`**: picks the backend (`MODEL_BACKEND=llm|rubric`, default
  `llm`; auto-falls-back to `rubric` with a warning if
  `ANTHROPIC_API_KEY` is unset) and writes `decisions.json` plus
  `run_meta.json` recording which backend *actually* ran — the UI reads
  this rather than the configured setting, so the provenance header can't
  lie about what produced the decisions on screen.

### Stage 4 — serve (`src/serve/`)

FastAPI, reads processed JSON per-request (so pipeline re-runs show up on
refresh). Routes: `GET /`, `GET /api/health`, `GET /api/branches`
(features joined with decisions), `GET /api/communities` (assignments
joined with centroid + population), `GET /api/network` (stats + actual
model backend + data sources + pipeline run timestamp).

Frontend (`static/`): single page, Leaflet + OSM tiles, centred on Dubai
(25.2048, 55.2708, zoom 11). Branch markers colored by action, radius ∝
population served; a toggleable community layer and assignment-line
layer; sibling-branch proximity lines on selection; a side panel with the
full feature table vs. network medians, decision + rationale + key
drivers + caveats; an "Assumptions" toggle rendering the known-limitations
list on the page itself, not buried in a README. Estimated/imputed values
render with a `~` prefix. Every LLM-originated string (`rationale`,
`caveats`, `key_drivers`) is HTML-escaped before touching the DOM — it's
untrusted text, not markup.

## Scope decisions made during the build

The original design brief was written as a prompt for a human running
real scrapers against real sites. Six gaps/bugs surfaced once it actually
got built and reviewed — recorded here because they're genuine design
decisions, not implementation noise:

1. **Live enrichment is stubbed, not implemented.** `ENABLE_SCRAPE=1` /
   `DUBAI_PULSE_ENABLED=1` exist as real flags with real
   fallback-and-log-loudly logic, but the live-fetch functions
   deliberately raise `NotImplementedError` rather than scrape real
   sites — iterating a scraper against a live site's structure without
   being able to re-verify it repeatedly risked silent breakage, and the
   brief's own done-state only requires the seed path to work. (A later,
   separate research pass *did* attempt the real fetching interactively —
   see "What's actually in the seed data" below for what that found.)
2. **Price-estimate flagging.** `Branch` has no "this was backfilled"
   field, so `prices.py` writes backfilled branch IDs to
   `price_flags.json`, and `build.py` folds `avg_price_aed` into
   `BranchFeatures.estimated_fields` for those branches — same discipline
   as population estimation.
3. **A contested-formula bug, self-inflicted in the original plan.** The
   formula for `nearest_km == 0` was originally written as
   `else True`, but the math is backwards: as `nearest_km → 0` with
   `second_km` fixed positive, the ratio `second_km/nearest_km → ∞`,
   which is never `< contest_ratio`. Correct formula: `else second_km ==
   0` — a community exactly co-located with its nearest branch is
   contested only if a second branch is tied at the same spot too.
4. **Zero known branch prices.** Real research (2GIS, Fresha,
   Groupon/Cobone, social media) found no source exposing a per-branch
   price for any of the 9 real Dubai branches. `backfill_missing_prices`
   originally assumed at least one branch would have a real price to
   compute a median from; with zero, `statistics.median([])` would crash
   the pipeline. Fix: a documented fallback constant
   (`FALLBACK_PRICE_AED = 99.0`, the one real Bedashing price point found
   anywhere — a "Blow Dry for AED 99" promo, chain-wide not
   branch-specific), applied to every branch with every branch flagged
   as estimated.
5. **A stale, conflicting `DecisionModel` Protocol.** An early draft put
   a per-branch-signature Protocol in `src/models.py`; a later draft
   independently defined the real, batched-signature Protocol in
   `src/model/base.py` without removing the first one. Dead code, but a
   same-named trap — removed, `src/model/base.py`'s version is canonical.
6. **The side panel permanently blocked the layer toggles.** Both
   elements were positioned at the identical `top: 50px; right: 10px`,
   and the side panel (once opened by any marker click — the map's core
   interaction) had no close button, so the toggles became unreachable
   for the rest of the session. Fixed by repositioning and adding a close
   button.

A final whole-branch review (after all 16 tasks) found one more class of
issue worth recording: the provenance header could say "backend: llm"
while displaying rubric-generated decisions (Stage 3's `run_meta.json`
fix above was the result), population imputation wasn't being flagged in
the UI the way price imputation was, and the rubric's `key_drivers` was
comparing raw deviations across incommensurate scales (population ~10⁴
vs. a 0–1 share) so population always "won" regardless of which feature
actually stood out — all three are fixed in the current code.

## What's actually in the seed data, and its real limits

- **9 real Dubai branches** (2GIS's UAE branch-aggregation page for
  ratings/reviews, cross-checked for area/head-office exclusion). This is
  the true count, not a research shortfall — Bedashing has 23 branches
  UAE-wide and the rest are outside Dubai.
- **50 real Dubai communities**, population from the DSC 2022/2024
  Population Bulletin (via a Wikipedia mirror, since `dubaipulse.gov.ae`
  is blocked — see below).
- **Branch prices: genuinely unavailable, not just hard to fetch.**
  Checked three separate times, the last with a real browser (Playwright)
  actually rendering Fresha's pages rather than a plain HTTP fetch.
  Conclusion: Bedashing has no partnered listing on Fresha anywhere — the
  pages that exist are unclaimed "discovery" pages with service *names*
  and zero prices attached. No per-branch price exists at any source
  checked. All 9 branches carry the fallback constant and are flagged
  estimated.
- **Community gender split: unavailable for a structural reason, not a
  network fluke.** `dubaipulse.gov.ae` and `dsc.gov.ae` both block
  automated access (Akamai/Imperva WAF), confirmed with a real browser.
  More importantly: the actual DSC Population Bulletin PDF (recovered via
  the Wayback Machine to check directly) does not publish a
  per-community gender split at all — only emirate-wide. That granularity
  may exist behind DSC's paid/registered API, not available here. All 50
  communities' female population is estimated via a global share (49%)
  and flagged as such.

Net effect: every `avg_price_aed` and every `population_female` in this
dataset is an estimate, not a reported figure. The pipeline flags both
and the frontend renders estimated values with a `~` prefix — the "do not
silently impute" principle holding up under its own worst case.

## Known limitations (the experiment log, not a disclaimer)

Rendered on the page itself behind the "Assumptions" toggle:

1. Nearest-branch assignment is false. Real choice depends on travel
   time, malls, parking, habit, price and brand. Straight-line distance
   from a community centroid ignores all of it.
2. Community centroids are not where people live. Large communities get
   collapsed to a point.
3. No competitors. A branch with five rival salons next door looks
   identical to one with none. The single biggest omission.
4. Female population is a poor demand proxy on its own — and in this
   build, *every* value is an estimate (see above), not just "a proxy
   that could be refined."
5. No revenue, footfall, staffing or lease data, so "SHRINK" here cannot
   distinguish a badly-located branch from a well-located, badly-run one.
6. The LLM classifies without ground truth and will produce
   confident-sounding labels regardless. Agreement with the rubric is a
   sanity check, not validation.
7. Prices are not "a thin basket that may not be current" — there are
   zero real per-branch prices anywhere, confirmed, not merely unsourced.
8. Dubai only.

## Run it

```bash
uv sync --extra dev
just all      # acquire -> features -> model
just serve    # http://localhost:8000
just test     # 58 tests
```

No API key or network access required for the guaranteed path. To use the
LLM backend, copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY`.
Flip backends directly: `MODEL_BACKEND=rubric uv run python -m
src.model.run` vs. `MODEL_BACKEND=llm ...` — re-running both populates an
llm-vs-rubric agreement comparison printed to stdout.

Done-state: a fresh clone, no API key, no network, `just all && just
serve` shows a Dubai map with every branch coloured by a rubric-derived
action, clicking one shows its features against network medians, and the
assumptions list is visible.

## First things to poke at once it's running

Not build tasks — the reason the thing exists:

- Flip `MODEL_BACKEND` and find branches where LLM and rubric disagree.
  Read the LLM's rationale on those. Is it seeing something, or
  confabulating?
- Change `CONTEST_RATIO` from 1.25 to 1.1 and 1.5. Do the SHRINK labels
  move? If a threshold nobody justified swings the answer, the model is
  too fragile to defend.
- Delete a high-population branch from the seed and re-run. Where does
  its population go, and does any neighbour flip to PROTECT? That's your
  cannibalization story in crude form.
- Compare the map against where Bedashing actually opened. If the model
  thinks their real sites are bad, either it's wrong or you've found
  something.
